# Стандарт кодування проєкту ClinicReception

Версія 2.0 від 22.11.2026. Власник: Вовк Давід (група 471). Попередні версії
1.0–1.2 діяли з ЛР 1 до ЛР 8; що змінилося, записано в
[журналі рішень](docs/standard/decisions.md).

Пов'язані файли: [чекліст огляду коду](docs/standard/review-checklist.md),
`.editorconfig`, `Directory.Build.props`, `CodeMetricsConfig.txt`,
`src/ClinicReception.Core/BannedSymbols.txt`, `scripts/check-source.sh`.

## 1. Сфера дії, рівні обов'язковості, глосарій

### 1.1. Сфера дії

Стандарт діє для всього коду, який пишеться вручну:

| Проєкт | Діє | Винятки |
| --- | --- | --- |
| `src/ClinicReception.Core` (бібліотека логіки) | повністю | немає |
| `src/ClinicReception.App` (консольний застосунок) | повністю | S-15 не стосується: застосунок і є місцем для консолі |
| `tests/ClinicReception.Tests`, `tests/Legacy.Tests` | повністю | C-06 (XML-документація) і N-10 для імен тестів, див. N-13 |
| `src/Legacy` (успадкований модуль ЛР 6) | лише F-01, F-11 і правила комітів | решту не перевіряють, борг TD-06 |

Стандарт не діє для згенерованого коду (`obj/`, `bin/`, файли `*.g.cs`) і для
гілки-пісочниці `ci-demo`, у якій правила порушують навмисно. Версія 2.0 діє з
22.11.2026 для всіх комітів у `main`. Код, написаний раніше, приводиться до неї
за правилом бойскаута (розділ 7.3).

### 1.2. Рівні обов'язковості

| Рівень | Значення | Наслідок порушення | Діагностика в `.editorconfig` |
| --- | --- | --- | --- |
| ОБОВ'ЯЗКОВО | виконують завжди | збірка падає або зміну не приймають на огляді | `error` |
| РЕКОМЕНДОВАНО | виконують, якщо немає вагомої причини вчинити інакше | зауваження на огляді, причину відступу пишуть у коментарі | `suggestion` |
| ДОПУСКАЄТЬСЯ | обидва варіанти прийнятні | зауважень не роблять | `silent` або `none` |
| ЗАБОРОНЕНО | конструкція в проєкті не вживається | збірка падає або зміну не приймають | `error` |

Рівень `warning` у проєкті не вживається. Через `TreatWarningsAsErrors` він
однаково ламає складання, тож назва рівня вводила б в оману (рішення SD-01).

У стандарті 89 правил: 52 ОБОВ'ЯЗКОВО (58 %), 6 ЗАБОРОНЕНО, 28 РЕКОМЕНДОВАНО і
3 ДОПУСКАЄТЬСЯ. З 52 обов'язкових правил 38 повністю або частково перевіряють
збірка, тести чи конвеєр CI, решту - рецензент за чеклістом.

### 1.3. Нумерація

Кожне правило має ідентифікатор, на який посилаються в коментарях огляду
(«порушено N-09») і в коментарях `.editorconfig`.

| Префікс | Розділ |
| --- | --- |
| N | іменування |
| F | форматування й структура файлу |
| C | коментарі й документація |
| D | дані й типи |
| X | правила предметної області: часові слоти й межі інтервалу |
| S | керуючі конструкції та складність |
| A | машинна частина й порядок роботи з правилами |
| K | коміти (додаток) |

### 1.4. Шаблон запису правила

Кожне правило записано так: ідентифікатор і формулювання, рівень, обґрунтування,
приклад, спосіб перевірки. Приклад у повній формі:

**N-09. Приватне поле - `_camelCase`, константа й статичне поле лише для читання - PascalCase.**
Рівень: ОБОВ'ЯЗКОВО.
Обґрунтування: підкреслення відрізняє поле від параметра й локальної змінної без
`this.`, тож у методі на 20 рядків не треба повертатися до початку класу, щоб
зрозуміти, звідки взялося значення.
Приклад: `private readonly List<VisitLine> _lines;`, а не `private List<VisitLine> lines;`.
Перевірка: IDE1006, правила `priv_underscore`, `const_pascal`, `static_readonly_pascal`, рівень `error`.

Правило без способу перевірки вважається побажанням: його або доводять до
перевірного вигляду, або знижують до РЕКОМЕНДОВАНО.

### 1.5. Глосарій предметної області

| Поняття | Ідентифікатор | Пояснення |
| --- | --- | --- |
| запис на прийом | `Appointment` | документ: пацієнт, лікар, послуги й стан запису |
| послуга в записі | `VisitItem` | позиція документа: код, кількість, ціна, тривалість |
| пацієнт | `Patient` | учасник, для якого створюють запис |
| лікар | `Doctor` | об'єкт обліку з кабінетом, вартістю консультації й довжиною слота |
| стан запису | `VisitStatus` | `Scheduled`, `Confirmed`, `Completed`, `Missed`, `Cancelled` |
| код послуги | `ServiceCode` | рядок до 20 символів, великими літерами, наприклад `LAB-02` |
| ціна за одиницю | `UnitPrice` | гривні без ПДВ, `decimal` |
| тривалість послуги | `DurationMinutes` | ціле число хвилин на одну одиницю |
| сума позиції | `Amount` | кількість, помножена на ціну |
| сума за прайсом | `Subtotal` | сума позицій до знижок |
| постійний пацієнт | `IsRegular` | ознака знижки для постійних пацієнтів |
| страховий поліс | `HasInsurance` | ознака страхової знижки |
| політика ціни | `IPricingPolicy` | правило, що дає ціну послуги з урахуванням знижки |
| сховище записів | `IAppointmentRepository` | додає й знаходить записи |
| сповіщення пацієнта | `INotifier` | надсилає повідомлення про запис |
| порушення правила | `DomainRuleException` | виняток з ідентифікатором правила, наприклад `appointment.transition` |
| барикада вводу | `VisitItemParser` | розбір рядка з консолі на межі застосунку |
| час початку й кінця прийому | `StartTime`, `EndTime` | межі напіввідкритого інтервалу, див. X-01 |
| дата прийому | `VisitDate` | `DateOnly` |
| слот прийому | `TimeSlot` | інтервал у розкладі лікаря (з'явиться в СР 3) |

Синонімів у коді немає: пацієнт ніде не називається `Client` чи `Customer`, а
запис - `Booking` чи `Reservation`.

## 2. Іменування

**N-01. Ідентифікатори англійською, терміни беруться з глосарію 1.5.**
Рівень: ОБОВ'ЯЗКОВО. Обґрунтування: одне поняття з одним іменем знаходиться
пошуком за секунду, а транслітерація (`Pacient`, `kolvo`) не знаходиться взагалі,
бо кожен пише її по-своєму. Перевірка: чекліст, пункт 1.

**N-02. Простір імен - `ClinicReception.<Проєкт>.<Тека>`, не глибше двох рівнів під коренем проєкту.**
Рівень: ОБОВ'ЯЗКОВО. Обґрунтування: простір імен збігається з текою, тож за
`using` одразу видно, де лежить файл. Перевірка: IDE0130, рівень `error`.

**N-03. Клас, запис, структура й делегат - PascalCase, іменник в однині.**
Рівень: ОБОВ'ЯЗКОВО. Обґрунтування: так названо всі типи .NET, інший стиль у
власному коді читається як помилка. Перевірка: IDE1006, правило `members_pascal`.

**N-04. Інтерфейс - `I` + PascalCase, називає роль: `IPricingPolicy`, `INotifier`.**
Рівень: ОБОВ'ЯЗКОВО. Перевірка: IDE1006 (`interface_prefix`), CA1715.

**N-05. Перелічення - в однині, члени без префікса типу; множина лише для `[Flags]`.**
Рівень: ОБОВ'ЯЗКОВО. Обґрунтування: змінна типу `VisitStatus` містить один стан,
тож `VisitStatuses` бреше про вміст. Перевірка: CA1714, CA1717.

**N-06. Параметр узагальненого типу - `T` або `T` + опис (`TResult`).**
Рівень: ОБОВ'ЯЗКОВО. Перевірка: CA1715.

**N-07. Метод - PascalCase. Команда називається дієсловом (`Confirm`, `AddItem`), запит - іменником із `Of` (`TotalOf`, `PriceOf`); асинхронний метод має суфікс `Async`.**
Рівень: ОБОВ'ЯЗКОВО. Обґрунтування: за ім'ям видно, чи метод змінює стан, і
читач не відкриває тіло, щоб це з'ясувати. Перевірка: IDE1006 (`members_pascal`,
`async_suffix`); дієслово чи запит - чекліст, пункт 2.

**N-08. Властивість - PascalCase, іменник; булева властивість починається з `Is`, `Has`, `Can`.**
Рівень: ОБОВ'ЯЗКОВО. Перевірка: IDE1006; булевий префікс - чекліст, пункт 2.

**N-09. Приватне поле - `_camelCase`, константа й статичне поле лише для читання - PascalCase.**
Рівень: ОБОВ'ЯЗКОВО. Повний запис наведено в 1.4. Публічних полів немає,
назовні дані видно лише через властивості.

**N-10. Параметр і локальна змінна - camelCase повним словом; одна літера лише для лічильника циклу.**
Рівень: ОБОВ'ЯЗКОВО для camelCase, повне слово перевіряє рецензент.
Перевірка: IDE1006 (`locals_camel`), чекліст, пункт 1.

**N-11. Подія називається дієсловом у минулому часі (`StatusChanged`), тип обробника - `EventHandler<T>`.**
Рівень: РЕКОМЕНДОВАНО. Обґрунтування: подій у проєкті поки немає, правило
задано наперед, щоб перша з них не з'явилася як `OnStatus`. Перевірка: чекліст.

**N-12. Колекція - іменник у множині (`Items`, `_lines`), словник - за ключем (`PricesByCode`).**
Рівень: РЕКОМЕНДОВАНО. Перевірка: чекліст, пункт 1.

**N-13. Тест - `Метод_Умова_Результат`, клас тестів - `<Тип>Tests`, дублер - за роллю (`FakeAppointmentRepository`, `StubPricingPolicy`, `FixedClock`).**
Рівень: ОБОВ'ЯЗКОВО. Обґрунтування: ім'я впалого тесту в журналі конвеєра має
пояснювати, що зламалося, без відкриття файлу. Підкреслення дозволені лише тут,
CA1707 для теки `tests` вимкнено. Перевірка: чекліст, пункт 14.

**N-14. Один тип на файл, ім'я файлу дорівнює імені типу.**
Рівень: ОБОВ'ЯЗКОВО. Перевірка: SA1402, SA1649.

**N-15. Величина з одиницею виміру містить одиницю в імені: `DurationMinutes`, `SlotMinutes`.**
Рівень: ОБОВ'ЯЗКОВО. Обґрунтування: `int Duration` не каже, хвилини це чи
секунди, і помилку в 60 разів не видно ні компілятору, ні тесту з «круглими»
числами. Перевірка: чекліст, пункт 3.

**N-16. Булевий член формулюється без заперечення: `IsValid`, а не `IsNotValid`.**
Рівень: РЕКОМЕНДОВАНО. Обґрунтування: `!IsNotValid` читач розгортає двічі.
Перевірка: чекліст.

**N-17. Заборонені форми імені (таблиця нижче).**
Рівень: ЗАБОРОНЕНО. Перевірка: чекліст, пункт 1.

| Антипатерн | Приклад, якого немає бути | Чим шкодить |
| --- | --- | --- |
| ім'я-затичка | `data`, `info`, `temp`, `obj`, `item1` | нічого не каже про вміст |
| транслітерація | `kolvo`, `Pacient`, `vizyt` | не знаходиться пошуком, кожен пише по-своєму |
| угорська нотація | `strCode`, `iQty` | тип і так видно, а префікс бреше після зміни типу |
| нестандартне скорочення | `CalcTot`, `apptSvc` | читач гадає, що мав на увазі автор |
| «And» в імені | `SaveAndNotify` | ознака двох обов'язків в одному методі |
| беззмістовний суфікс | `AppointmentManager`, `VisitHelper`, `Utils` | клас без чіткої відповідальності |
| числовий суфікс | `Calculate2`, `VisitFinal` | незрозуміло, чим версії відрізняються |
| ім'я, що бреше | `GetTotal`, який ще й змінює стан | виклик «запиту» несподівано змінює дані |

### 2.1. Приклади «погано / добре»

Пара 1. Транслітерація й ім'я-затичка (з успадкованого модуля ЛР 2).

```csharp
// ПОГАНО
int kolvo = 0;
foreach (string[] t in ln) { kolvo++; }
```

```csharp
// ДОБРЕ
int lineCount = 0;
foreach (VisitLine line in _lines) { lineCount++; }
```

`kolvo` ще й бреше: змінна рахує рядки послуг, а не кількість одиниць. Це
з'ясувалося лише після перейменування (борг Б-1 з ЛР 2).

Пара 2. Угорська нотація.

```csharp
// ПОГАНО
string strCode = parts[0];
int iQty = int.Parse(parts[1]);
```

```csharp
// ДОБРЕ
string serviceCode = parts[0];
int quantity = int.Parse(parts[1], CultureInfo.InvariantCulture);
```

Префікс повторює тип, який і так видно в оголошенні, а після зміни типу на
`long` ім'я `iQty` почне брехати.

Пара 3. Скорочення й однобуквені параметри.

```csharp
// ПОГАНО
public decimal CalcTot(List<VisitItem> l, int t)
```

```csharp
// ДОБРЕ
public decimal TotalOf(IReadOnlyList<VisitItem> items, IPricingPolicy pricing)
```

`l` і `t` неможливо знайти пошуком, а `t` - ще й число, зміст якого знає лише
автор. У другому варіанті тип параметра каже, звідки береться ціна.

Пара 4. «And» в імені (за мотивами класу-Бога з ЛР 4).

```csharp
// ПОГАНО
public void SaveAndNotify(Appointment appointment)
```

```csharp
// ДОБРЕ
_repository.Add(appointment);
_notifier.Notify(patient.Email, text);
```

Два обов'язки в одному методі означають дві причини його змінювати. Після
розділення збереження й сповіщення тестуються окремо.

Пара 5. Беззмістовний суфікс.

```csharp
// ПОГАНО
public class AppointmentManager
```

```csharp
// ДОБРЕ
public sealed class AppointmentService
public static class AppointmentCsvReport
```

`AppointmentManager` у ЛР 4 рахував ціну, писав файл, надсилав листи й друкував
звіт: суфікс дозволив покласти в клас усе. Ім'я з однією роллю цього не дозволяє.

Пара 6. Ім'я методу не пояснює, що він робить (успадкований модуль ЛР 2).

```csharp
// ПОГАНО
public decimal ProcessData(bool f)
```

```csharp
// ДОБРЕ
public decimal CalculateTotal(bool hasInsurance)
```

`ProcessData` підходить будь-якому методу, а `f` змушує відкрити тіло, щоб
дізнатися, що прапорець означає страховий поліс.

Пара 7. Ім'я, що бреше (так поводився метод-монстр з ЛР 3).

```csharp
// ПОГАНО
public decimal GetTotal(Visit visit)
{
    decimal total = ...;
    visit.Status = "Confirmed";
    return total;
}
```

```csharp
// ДОБРЕ
decimal total = service.TotalOf(appointment);
service.Confirm(appointment.Id);
```

Виклик «запиту» з префіксом `Get` мовчки підтверджував візит. Після поділу на
запит і команду кожне ім'я каже правду.

Пара 8. Булевий член без префікса.

```csharp
// ПОГАНО
public bool Insurance { get; init; }
if (patient.Insurance == true) { ... }
```

```csharp
// ДОБРЕ
public bool HasInsurance { get; init; }
if (patient.HasInsurance) { ... }
```

`Insurance` читається як об'єкт поліса, а не як так/ні, і провокує порівняння
з `true`.

Пара 9. Одиниця виміру.

```csharp
// ПОГАНО
public int Duration { get; }
```

```csharp
// ДОБРЕ
public int DurationMinutes { get; }
```

Тривалість ЕКГ 15 і тривалість 900 однаково правдоподібні, якщо не знати
одиниці. Ім'я знімає питання.

Пара 10. Межі інтервалу.

```csharp
// ПОГАНО
public TimeOnly From { get; }
public TimeOnly To { get; }
```

```csharp
// ДОБРЕ
public TimeOnly StartTime { get; }
public TimeOnly EndTime { get; }
```

`To` залишає відкритим питання, чи входить кінець у прийом. Пара
`StartTime`/`EndTime` разом із X-01 відповідає на нього однаково по всьому коду.

Пара 11. Стан числом.

```csharp
// ПОГАНО
public int Status;   // 0-новий, 1-підтв., 2-закр.
```

```csharp
// ДОБРЕ
public VisitStatus Status { get; private set; }
```

Коментар-легенда застаріває першим, а перелічення не дає записати стан 17.

## 3. Форматування, структура файлу, коментарі

### 3.1. Форматування й структура файлу

**F-01. Відступ - 4 пробіли, табуляція заборонена; у `.csproj`, `.props`, `.json`, `.yml` - 2 пробіли.**
Рівень: ОБОВ'ЯЗКОВО. Перевірка: `indent_style`, `indent_size`, IDE0055.

**F-02. Довжина рядка - до 120 символів.**
Рівень: РЕКОМЕНДОВАНО. Обґрунтування: на екрані 1920 пікселів у Visual Studio з
відкритим провідником рішення видно близько 130 символів шрифтом Consolas 10,
тож 120 вміщується без горизонтального прокручування. У режимі порівняння двох
версій поруч видно лише близько 85 символів, тому довгі рядки там переносяться.
Машинної перевірки немає: `max_line_length` компілятор не перевіряє, а в коді
лишилося 136 довших рядків (рішення SD-02, борг TD-09). Перевірка: чекліст для
нових рядків.

**F-03. Фігурні дужки в стилі Allman: кожна дужка на окремому рядку.**
Рівень: ОБОВ'ЯЗКОВО. Перевірка: `csharp_new_line_before_open_brace = all`, IDE0055.

### 4.6. Приклади «погано / добре»

Пара 16. Гроші в `double`.



`double` дає суми на кшталт 503,58499999999998, а `0.07` без імені не каже, що

Пара 17. Поточний час усередині бібліотеки (код `Visit` до версії 2.0).

```csharp
public Visit(string id, string patientName)
```

```csharp
public Visit(string id, string patientName, TimeProvider? clock = null)
```

Пара 18. Банківське заокруглення.

```csharp
// ПОГАНО
return Math.Round(total, 2);   // 0,125 -> 0,12
```

```csharp
// ДОБРЕ
return Money.Round(total);     // 0,125 -> 0,13
```

`Math.Round` без режиму заокруглює половину до парного, і в чеку виходить на
копійку менше, ніж порахує касир.

Пара 19. Перетин слотів.

```csharp
// ПОГАНО

    return false;
}
```


Перша умова не помічає прийому, що починається раніше й закінчується всередині

напіввідкриті інтервали однаково в усіх місцях.

### 5.2. Числові межі

| Метрика | Норма | Межа | Як перевіряється | Дія при перевищенні |
| --- | --- | --- | --- | --- |
| цикломатична складність методу | 6 | 10 | CA1502, збірка падає | Extract Method, таблиця замість ланцюга `if` |
| глибина вкладеності | 2 | 3 | огляд | запобіжні умови, Extract Method |
| логічних рядків у методі | 30 | 50 | огляд | декомпозиція |
| параметрів методу | 4 | 5 | огляд | об'єкт-параметр |
| полів у класі | 7 | 10 | огляд | Extract Class |
| публічних членів класу | 12 | 15 | огляд | поділ відповідальностей |
| рядків у файлі | 300 | 500 | огляд | поділ типу |

Складність рахується вручну так: 1 за метод і по 1 за кожен `if`, `else if`,
цикл, `case`, `catch`, `&&`, `||`, `??`, тернарний оператор і комбінатор `or`
у шаблоні. CA1502 комбінатора `or` не рахує: для `VisitItemParser.Parse` ручний
підрахунок дає 12, інструмент - 10, а якщо замінити два шаблони `is < 1 or > Max`
на `x < 1 || x > Max`, інструмент теж показує 12. Поріг 10 у `CodeMetricsConfig.txt`
тому стосується лічби інструмента.

### 5.3. Приклади «погано / добре»

Пара 20. Вкладені перевірки.

```csharp
// ПОГАНО
public decimal TotalOf(Appointment appointment)
{
    if (appointment != null)
    {
        if (appointment.Items.Count > 0)
        {
            decimal sum = 0m;
            foreach (VisitItem item in appointment.Items)
            {
                sum += _pricing.PriceOf(item);
            }
            return sum;
        }
    }
    return 0;
}
```

```csharp
// ДОБРЕ
public decimal TotalOf(Appointment appointment)
{
    ArgumentNullException.ThrowIfNull(appointment);

    decimal sum = 0m;
    foreach (VisitItem item in appointment.Items)
    {
        sum += _pricing.PriceOf(item);
    }

    return sum;
}
```

Глибина впала з чотирьох до двох, а `null` замість мовчазного нуля дає виняток,
який показує місце помилки, а не розбіжність у звіті через тиждень.

Пара 21. Ланцюг `if` за ключем (з методу-монстра ЛР 3).

```csharp
// ПОГАНО
if (promoCode == "CHECKUP10")
{
    total = total * 0.9m;
}
else if (promoCode == "MINUS200" && total > 1000)
{
    total = total - 200;
}
```

```csharp
// ДОБРЕ
return promoCode switch
{

    PricingRules.FixedPromoCode when amount > PricingRules.FixedPromoFrom
```

Промокоди читаються як таблиця, магічні числа зникли, а новий код додається

### 6.4. Обґрунтовані придушення

SA1309 забороняє підкреслення на початку імені поля, а N-09 його вимагає.
Правило StyleCop розраховане на стиль із `this.`, який стандарт не приймає;
залишити обидва правила означало б, що жодне поле не можна назвати правильно.

SA1101 вимагає `this.` перед кожним звертанням до члена класу. Поле й так
відрізняє префікс `_`, а `this.` додає шум у кожен рядок методу.

CA1031 придушено точково для верхнього обробника в `Program`: він єдиний має
перехоплювати будь-який виняток, щоб користувач побачив зрозуміле повідомлення,
а не стек викликів. Придушення оформлено атрибутом із `Justification` у
`src/ClinicReception.App/GlobalSuppressions.cs`; для решти коду правило діє.

Решта придушень (SA1633, SA1200, SA1623, SA1642, SA1413, CA1848) мають коментар
над рядком у `.editorconfig`.

## 7. Огляд коду, порівняння, порядок змін

### 7.1. Огляд коду

Чекліст огляду лежить у [docs/standard/review-checklist.md](docs/standard/review-checklist.md).
У ньому лише те, чого не бачить машина: відступи, порядок `using` і складність
перевіряє збірка.

Два правила культури огляду:

- зауваження стосується коду, а не автора: «у `TotalOf` два виходи з різними
  одиницями», а не «ти знову наплутав»;
- зауваження має бути виконуваним, тобто містити дію: «винесіть `0.93m` у
  `PricingRules.RegularPatientRate`», а не «незрозуміло».

### 7.2. Порівняння з публічними стандартами

Джерела: C# Coding Conventions і Identifier names на Microsoft Learn, coding-style.md
у репозиторії dotnet/runtime.

| Питання | Microsoft Learn | dotnet/runtime | Наш стандарт | Чому так |
| --- | --- | --- | --- | --- |
| відступ | 4 пробіли, без табуляції | 4 пробіли, без табуляції | 4 пробіли (F-01) | збігається з обома |
| дужки | Allman; для одного оператора не сказано | Allman; для одного рядка дужки можна не ставити | Allman, дужки завжди (F-04) | відступ 1 |
| приватне поле | `_camelCase`, статичне `s_` | `_camelCase`, статичне `s_`, `t_` | `_camelCase`, статичне readonly - PascalCase (N-09) | відступ 2 |
| `this.` | не сказано | лише коли необхідно | заборонено (N-09) | поле відрізняє `_` |
| `var` | коли тип зрозумілий з виразу | лише коли тип названо праворуч | лише коли тип видно, рівень підказки (D-03) | ближче до runtime |
| `int` чи `Int32` | ключові слова мови | ключові слова мови | ключові слова, `error` (D-04) | збігається |
| `using` | поза простором імен | поза простором імен, `System` першими | поза простором імен, `System` першими (F-08) | збігається з runtime |
| простір імен | файлового рівня | не сказано, у прикладі блоковий | файлового рівня (F-07) | мінус рівень відступу |
| довжина рядка | 65 символів (для статей документації) | не сказано | 120, рекомендовано (F-02) | відступ 3 |
| порядок членів | не сказано | поля на початку типу | константи, поля, конструктори, властивості, методи (F-06) | повніше за runtime |
| константи | PascalCase | PascalCase | PascalCase (N-09) | збігається |
| XML-документація | для публічних членів | не сказано | обов'язкова, `error` (C-06) | бібліотеку читають без вихідного коду |
| модифікатор доступу | не сказано | завжди, навіть типовий | завжди, крім членів інтерфейсу (A-07) | збігається з runtime |
| порожні рядки | щонайменше один між методами | не більше одного поспіль | рівно один (F-05) | поєднує обидва |
| `#region` | не сказано | не сказано | заборонено (F-10) | регіон ховає довжину класу |
| `new()` без типу | дозволено, коли тип збігається | лише коли тип названо зліва | дозволено, коли тип названо зліва | як у runtime |

Відступ 1. Дужки обов'язкові навіть для одного оператора, хоча dotnet/runtime
дозволяє їх не ставити для однорядкового тіла. У навчальному проєкті зміни
вносять швидко, і найпоширеніша помилка - дописати другий оператор під `if` без
дужок: він виконуватиметься завжди, а відступ створює ілюзію, що ні. Ціна
правила - один рядок, ціна помилки - дефект, якого не видно під час читання.

Відступ 2. Статичні поля лише для читання (`AllowedTransitions`) названо в
PascalCase, а не з префіксом `s_`. У проєкті такі поля - це таблиці правил, які
ніколи не змінюються після ініціалізації, тобто за змістом вони константи. StyleCop
(SA1311) вимагає для них PascalCase, а `s_` нічого не додає, поки змінних
статичних полів у коді немає. Якщо такі з'являться, правило доведеться
переглянути.

Відступ 3. Межа рядка 120 символів замість 65 з Microsoft Learn. Межа 65 написана
для статей документації, які читають з телефона, а наш код читають у Visual
Studio на моніторі 1920 пікселів. При 65 символах довгі сигнатури з XML-коментарями
розпадаються на багато рядків і читаються гірше, а 120 вміщується на екрані без
прокручування.

Відступ 4. `this.` заборонено, хоча Microsoft Learn про нього мовчить, а
dotnet/runtime лише радить уникати. Повна заборона робить код однаковим: у змішаному
стилі читач щоразу гадає, чому в одному місці `this.` є, а в іншому немає.

### 7.3. Порядок внесення змін до стандарту

1. Запропонувати зміну може будь-хто з команди: issue на GitHub з міткою
   `standard` або коментар в огляді коду з посиланням на правило.
2. Пропозиція містить формулювання правила, обґрунтування, приклад «погано /
   добре», спосіб машинної перевірки і кількість місць у коді, які доведеться
   змінити (вивід збірки з новим правилом).
3. Рішення ухвалює власник стандарту після обговорення. Правило приймається,
   якщо воно перевірне й ніхто з команди не наводить прикладу, де воно
   шкодить; інакше рівень знижують до РЕКОМЕНДОВАНО.
4. Рішення записується в [журнал рішень](docs/standard/decisions.md) з номером
   SD-NN, датою, варіантами й наслідками, а зміна стандарту йде одним комітом
   разом із `.editorconfig`.
5. Версія стандарту змінюється за семантичним версіюванням: нове або посилене
   правило - старша версія (2.0 → 3.0), нове РЕКОМЕНДОВАНЕ правило чи уточнення
   формулювання - молодша (2.0 → 2.1), виправлення тексту без зміни змісту -
   латка (2.0.1).
6. Перехідний період - правило бойскаута: файл, якого торкнулися, лишають
   чистішим, ніж він був. Невиправлені місця записують у реєстр боргу з
   терміном: для версії 2.0 це TD-09 (довгі рядки), строк - до кінця СР 3.
   Машинне правило вмикається з рівнем `error` лише тоді, коли код уже
   відповідає йому (A-06).
7. Шкідливе правило скасовують тим самим порядком: пропозиція з прикладом шкоди,
   запис у журналі рішень, зниження рівня або видалення з `.editorconfig` і
   нова версія стандарту.
